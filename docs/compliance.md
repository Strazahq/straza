# Compliance mapping: NIS2, ISO/IEC 27001, EU AI Act (and neighbors)

No product is NIS2 compliant, ISO certified or AI Act compliant by itself.
NIS2 obligations bind the *operator* (essential/important entities), ISO/IEC
27001 certifies an organization's ISMS, and the AI Act binds providers/deployers of *AI systems* and GPAI
*models* (there is no AI Act product certification at all). What a product can
do is (a) give operators the controls and evidence they need, and (b) be built
the way those frameworks expect. This document maps both directions and lists
the gaps.

Context: **NIS1** (Directive 2016/1148) is repealed; **NIS2** (Directive
2022/2555) applies since 2024-10-18 (member-state transpositions vary, so read
your own country's act). AI coding agents acting on production code and
internal systems squarely fall under "policies on access control", "supply chain security" and "use of secure authentication" for
covered entities, and that is Straza's job.

## 1. What Straza gives a NIS2-covered operator (Art. 21(2) measures)

| NIS2 Art. 21(2) | Straza contribution |
|---|---|
| (a) risk analysis & security policies | PolicySet as versioned, auditable policy-as-code for agent actions; policy snapshots signed and content-addressed (what was enforced, when, provably). |
| (b) incident handling | Kill switch: an identity manager deactivation revokes every session of the person, and connected clients drop them in under two seconds on the demo stack; per-session revocation; a hash-chained audit trail (`strazactl audit verify`). Every web and CLI login success or refusal is a chained `straza.audit.authn` event with source IP and user agent, and so is every session a person signs out or an admin revokes. A session the idle or lifetime sweeper closes is such an event too, without the source IP and user agent. |
| (c) business continuity | Stateless data plane (any pod serves any session), self-validating tokens survive restarts, fail-closed degradation semantics are specified (the fail-closed behavior is described on the [security model](https://docs.straza.ai/security/security-model/) page), Postgres/NATS HA per operator infra. The break-glass admin signs in at the server's own emergency page in both profiles, so an identity provider outage or a provisioning mistake never locks the control plane. |
| (d) **supply chain security** | Which tools each role can see and call, sandboxed tool containers, and upstream credentials injected on the server so a third-party model never holds them. |
| (e) security in acquisition/development/maintenance | Governs the agents doing the development: default-deny profiles, interpreter tagging, attestation-gated tokens on developer endpoints. The hook on a machine where the agent can run anything is advisory and not a security boundary, and an MCP server a user adds to a harness outside the gateway is that user's responsibility. |
| (f) effectiveness assessment | Conformance corpora + assertion-backed demos are replayable evidence; audit chain supports control testing. |
| (g) cyber hygiene & training | Knowledge packs deliver role-bound instructions/guardrails into every session. |
| (h) cryptography policies | Ed25519 signatures (tokens, snapshots), TLS 1.2 or newer, secretbox at rest; the transport defaults are on [TLS and exposure](https://docs.straza.ai/guides/operate/tls-and-exposure/) and the keys on [Keys, certificates and tokens](https://docs.straza.ai/security/keys-certificates-and-tokens/). strazad can bind a machine's enrollment to an Ed25519 key that stays on the machine. Every session token minted from that key carries the key's thumbprint (`cnf.jkt`), and every request with such a token must carry a fresh DPoP proof (RFC 9449) signed by the key over a server nonce, so a copied key-bound token works nowhere else. The straza client keeps that key in `straza service`, which on a managed machine runs under its own OS account, and its bearer device credential is retired. An AI agent's session is bound by a proof from the same service's key when it checks in through the service. `straza service` runs on Linux and Windows in this release, on Windows as the Windows service straza-service under the virtual account NT SERVICE\straza-service. |
| (i) HR security & **access control** | IGA-native: SCIM lifecycle from the identity manager (joiner/mover/leaver), roles carry policy, tools and knowledge, sessions as principals, time-boxed assignments (`valid_from/valid_to`). A role can cover only some objects of a server that pins an object type, such as some repositories of a GitHub organization, and the role's SCIM group carries that line as `covers` (scim-profile rev 21). An agent's git fetch or push through Straza is decided as a call of the server's git tool, so the same roles and objects govern git (app-manifest rev 9, spec/grant). |
| (j) **MFA / secure authentication** | Enterprise: sign-in is delegated to your identity provider over OIDC, so its MFA and passkeys apply, and attestation adds a machine factor. The standalone issuer uses passwords hashed with bcrypt, and passkeys for it are on the roadmap. The break-glass account signs in with a password in both profiles, outside the identity provider's MFA. A person's key enrollment lasts until a defined, enforced sign-in deadline: `governance.signInMaxAge`, 7 days by default in both profiles, and never renewed by use. A browser sign-in asks the identity provider for a new authentication, and strazad accepts it only when its ID token names the enrolling key and its `auth_time` is at most 10 minutes old. The deadline counts from the ID token's `auth_time` when the token carries one not more than 1 minute ahead of the server's clock, and from the key enrollment otherwise. A device code sign-in follows the identity provider's own session policy, and `governance.minSignIn` refuses it, by default on enterprise. NIS2 names no number, and NIST SP 800-63B-4 sets 24 hours at AAL2, so a deployment under an AAL2 policy lowers the setting and sets the identity provider's reauthentication period to match. AI agents and service accounts have no such enrollment, because they prove themselves fresh at every session start. Their sessions are bound to the key of `straza service` when they check in through it with a DPoP proof, and a check-in without a proof is refused on enterprise and still gets a bearer token on standalone. The straza client's bearer device credential is retired, so every person's straza enrollment is a key enrollment under this deadline. strazactl keeps its device credential with a 30-day renewing lifetime. |
| Art. 23 incident reporting (24 h / 72 h) | Audit events are CloudEvents with timestamps and principals; SIEM sinks (an HMAC-signed webhook and a JSONL file, delivered at least once; see [Sinks and SIEM](https://docs.straza.ai/guides/operate/sinks-and-siem/)) feed the operator's reporting pipeline. Straza provides the evidence, not the report. |

## 2. ISO/IEC 27001:2022 Annex A: main touchpoints

| Control | Straza |
|---|---|
| A.5.3 segregation of duties | Only a person publishes a draft from the drafts routes. The drafts publish route refuses an admin API token and an AI agent whatever scopes or roles they hold, and refuses a session a coding harness checked in. The publisher needs standing over every object in the draft, the standing the direct route for that object asks (events revision 37). An admin API token keeps every direct write it has today: each is a one-item draft of the api door that the token publishes in the same request, so automation never waits. `admin.secondPerson` adds the second person. It is file-only, off by default in both profiles, and `GET /v1/admin/config` shows it as `admin.second_person`. While it is on, a publish whose check lists a risk, which a change that widens access, a server removal and an AI agent's draft that loosens a policy set binding that same agent all raise, is refused to anyone who wrote a revision of the draft, to the person who minted an admin API token that wrote one, followed through tokens that minted tokens, and to the sponsor of an agent that wrote one. A token whose minter cannot be traced refuses every publisher. A direct admin write whose one-item check lists a risk is refused to every caller, root and tokens included, so such a change, a direct `DELETE` of a server included, goes through a draft that a second person publishes. A change whose check lists no risk publishes by its author, and pausing a server stays an immediate operation, so an incident response never waits (NIS2 21(2)(b)). The setting leaves two paths open. Assignments stay immediate operations, so a person can create a role nobody holds with an ungated access row, which widens nothing, and then assign it. The identity manager's approval of assignments closes that path. The second path is any credential of a person that an agent can read on that person's machine, which publishes as that person: an unexpired ID token, which the publish route accepts as every admin route does, the straza client's included. strazactl keeps no login on the machine, because it runs only on an admin API token, and a token never publishes. The `draft.publish` record names the publisher as `actor` and the author of the first revision as `proposer`. Only the person enrolls their own approver phone or browser, so nobody approves in another person's name. `POST /v1/admin/approvers/enroll-token` refuses every caller, whoever the body names, and writes one `enroll-token.refused` record in `straza.audit.admin` (events revision 56). The person mints their own enroll token on `POST /v1/approvals/self/enroll-token`, which refuses an admin API token and a session a coding harness checked in. |
| A.5.15 to A.5.18 access control, rights management | Role model fed by IGA, admin-gated grants, time-boxed assignments, immediate deprovisioning cascade that also removes the user's per-user OAuth grants with one audit record per grant, and every role grant that starts or ends, over the admin API, over SCIM or by a user delete, leaves one audit record naming the actor. |
| A.5.15, A.5.18 delegated entitlement definition, kept apart from assignment (also NIS2 21(2)(i)) | The team that owns an MCP server defines the entitlements that reach it and never hands them out. Every application role that reaches a server belongs to that server, whether the server's admin or a global admin made it, so each entitlement names the one server it reaches. A server admin creates roles their own server owns, names the tools each one reaches one by one and deletes the ones nobody holds, only a global admin gives such a role every tool and the tools the server adds later, and every verb is authorized on the stored column `owner_app_id`, never on the role's name. Granting a holder stays with the identity manager over SCIM, a role someone already holds has a tool list the server admin can neither widen nor delete, and a role a server owns implies no other role, so its reach never leaves that server. Each create and delete writes one `roles.create` or `roles.delete` record on `straza.audit.admin` naming the actor, the role and the server (events rev 33), and the SCIM group carries the owning server as an attribute (scim-profile rev 19, on every application role that reaches a server since rev 20) so a campaign can certify the family on its own. |
| A.5.15, A.5.18, A.8.2, A.8.3 access per object (also NIS2 21(2)(i)) | On an MCP server whose one credential reaches many objects, such as the repositories of a GitHub organization, a role's access row says which objects it covers: `covers: every`, or `covers: {objects: [...]}` with each object named, which strazad binds to the object's id in the server's object list so a rename keeps it (spec/objects rev 7). A person changes the line through a draft. A first pin, an unpin and migration 39's backfill change it in place and write no binding record (events rev 44). A server's admin may newly make a role the server owns cover every object only while `admin.serverAdminsCoverEvery` is true, its default, and a global admin always may. A row on a pinned server without a line covers nothing. The identity manager assigns and certifies the role as any other and reads the line from the read-only `covers` attribute of its group, one value per named object under the name the server's object list holds now, or `every` or `none` per access row, each with the server and the type in front (scim-profile rev 21), and a PATCH on it answers 400 mutability. A listing that renames an object puts each role that names it, and each role that composes one, on the change feed, so the identity manager reads the new name. An object the list no longer holds keeps the name it had when the role was published. The gateway checks every `tools/call` to such a server against every role the caller holds before the policy engine runs, so no rule can allow a call it refuses and no approval is spent on one. A tool that names its object needs a role that covers that object, and a tool that can reach every object, a tool whose calls do not name the object, and a tool the pinned declaration leaves out all need a role on every object. The first covering role by name is the role the record and the credential broker name. An unknown object gets the same refusal as an uncovered one, so the gateway never tells an agent which objects exist. With `apps.objects.enabled` false only roles on every object may call a tool that names an object, while a tool with reach `none` still answers any role that binds it, so turning the check off never widens access. The hook lane never runs this check. |
| A.5.15, A.8.3, A.8.5, A.8.15, A.8.24 git through a Straza grant (also NIS2 21(2)(i)) | An agent runs plain git against a git host such as GitHub, and no credential for that host sits on its machine. `straza service` asks strazad for a git grant at `POST /v1/grants`, and strazad decides the grant as a call of the tool that the server's `straza.git` block maps the operation to, such as `git_fetch` or `git_push` on ghapp, through the same decision a `tools/call` takes: visibility, the session's policy overlay, the rate limit, the object check, the policy engine and the approval (app-manifest rev 9). The roles, the objects a role covers and the approval rules that govern the tool therefore govern git. An approval's fingerprint carries the exact ref updates, so one approval runs one set of updates. The grant is an Ed25519 JWS from the session key set with `typ` `straza-grant+jwt`, valid for 120 seconds, naming one repository, one operation and on a push the exact updates, and bound to the machine's key by `cnf.jkt` (spec/grant v1alpha1). The resource server that holds the host's credential verifies the grant and a DPoP proof from that key on every request, while the session token verifier and the ID token verifier refuse a token with the grant's `typ`, so a grant opens nothing but git. Each issued grant and each refusal of the decision writes exactly one `straza.audit.mcp` record with the event `grant`, queued before the grant leaves strazad, and the grant's `dec` claim is that record's id, so the resource server's log line joins the chain (events rev 48). A force push is not detected, because the server sees only commit ids, so a branch rule at the git host blocks it. |
| A.5.16 identity management | People, AI agents and service accounts are identities, and sessions and devices are records you can list and revoke. AI agents arrive over SCIM with the agent extension that spec/scim-profile defines. Every user created or changed through the admin API or over SCIM, every approver enroll token and enrollment, every approver device a user delete removes (`approver.revoke`), and every AI agent key set or removed writes one chained `straza.audit.admin` record that names who acted (events revisions 40 and 41). |
| A.5.17 authentication information | Passwords hashed with bcrypt, admin API and SCIM tokens stored as SHA-256 hashes, server secrets sealed with secretbox, a one-time bootstrap password. Values in a server's manifest, its env entries included, are stored in plain text, so a credential goes into the server's secret and never into the manifest. strazactl holds no credential of its own. It runs only on an admin API token in `STRAZA_API_TOKEN`, which a person mints in the console with a scope and an expiry, so no admin credential sits on a machine unless a person puts a token there. strazad refuses strazactl's sign-in and its old device credential with one `straza.audit.authn` login failure, reason `strazactl no longer signs in` (events revision 55), and refuses a live session labelled strazactl. The client assertion key, which signs agents' clients in at the customer's identity provider, is sealed under the sealing key at rest, never leaves the server through any route, record or log line, and is managed by a full administrator only. In the manifest, an env value, an argument, or the user part, query, fragment and path of an address sit in clear in the database, its backups and an apps directory file. Every read masks them, the admin API, strazactl apps export, the console, health reasons, the server log and the error an AI agent reads included. Two gaps remain. A value the secret scan does not flag prints when the server itself writes it to its log. A drafts check still tells a caller who reads a server without apps:write whether a guessed unflagged value equals the stored one. One secret per server moves into a stored credential with credential.inject. A person's key enrollment keeps its private key on the machine, and of that key the server stores only the public half and its thumbprint. Its period is defined and enforced: `governance.signInMaxAge`, 7 days by default in both profiles, absolute from the person's authentication at the identity provider as the ID token's `auth_time` states it, or from the key enrollment when the token carries none, and checked at every key check-in and every refresh of a key-bound session. Past the deadline strazad refuses the next key check-in and the next refresh, so a session ends within one token lifetime, 300 seconds, of the deadline, even inside its 12 hours. ISO/IEC 27001 names no number, and NIST SP 800-63B-4 sets 24 hours at AAL2. A check-in counter at or below the last one accepted shows that the key was copied, so strazad revokes the device and writes one `straza.audit.identity` `device.key.reused` record (events revision 45). The straza client's own bearer device credential is retired: strazad refuses it at enrollment, at check-in and at refresh with one `straza.audit.authn` login failure (events revision 46), so a live session of an older client on a person's machine ends within 300 seconds. On standalone the cut does not reach an AI agent: its check-in without a proof still gets a bearer token, so an older client's agent keeps working, while enterprise refuses that check-in with one login failure. A key or client secret that once sat in the agent's reach stays valid until an admin registers the key `straza service` made with `strazactl users nhi-key set` and rotates the secret at the identity provider. Each person's key, an AI agent's key or client secret, and every session token then sit in `straza service`, so when the service runs under its own OS account the AI agent, which runs as the person, cannot read them. A service started with STRAZA_HOME runs as its caller and keeps the key in that account, which is custody `user`. `governance.minCustody`, `account` by default on enterprise, refuses a person's machine key whose enrollment reports it kept in the person's own account, at enrollment and at every later check-in and refresh. The kind is what the client reports, not a proof, so the setting does not stop a client that reports a false kind. An AI agent's key carries no custody, so only the deployment keeps an agent's service under its own OS account. On a person's browser sign-in, `straza service` alone holds the PKCE verifier and redeems the code, so neither the verifier nor the ID token passes through the person's processes, where an agent runs. |
| A.5.19 to A.5.23 supplier/cloud relationships | MCP servers are third-party suppliers: an admin installs each manifest, and the credential broker keeps the supplier credential on the server. |
| A.5.32 intellectual property rights | For the project: an outside contribution is merged only after each of its authors accepts the Contributor License Agreement on the pull request, and a pull request stays unmerged until the check in `.github/workflows/cla.yml` reports `straza/cla` green for every author. The check judges each author by the GitHub account, never by an email or a name, and refuses material that its author marks as excluded from the agreement. The Apache-2.0 directories `spec/`, `pkg/`, `adapters/`, `plugins/` and `kits/python/` each carry their LICENSE file, and every release archive, the container image and the console carry `THIRD_PARTY_NOTICES.txt` with the notices and license texts of the third-party software Straza ships. |
| A.5.33 protection of records | For the project: each acceptance of the Contributor License Agreement is recorded in a private repository, bound to the GitHub account's numeric id, the agreement's version and the SHA-256 of its text, and confirmed in writing on the pull request. Every run of the check reads the whole history of the pull request and records what an earlier run missed. |
| A.8.2 to A.8.5 privileged access, info access restriction, secure auth | Deny-by-default, including any harness tool Straza does not classify, which an admin allows only by its exact name and whose refusals the audit names (policyset rev 26, events rev 50), role-scoped tool visibility, attestation-gated tokens, gateway re-checks per call. Separation of duties on the admin plane has two axes. By area: `admin.roleAreas` maps roles to per-area grants (`area:read\|write`, 12 areas) and `wat_` admin API tokens carry the same per-area scopes, so an auditor seat reads audit without touching config or identity. By object: every MCP server names one role, minted at registration as `mcp-admin-` plus the server's namespace and name, and its holder administers that server alone, refused elsewhere with the role they would need. The product role `straza-global-mcp-admin` is boot-created and undeletable with the fixed meaning `apps:read, apps:write`, and `admin.roleAreas` refuses to narrow it. A token carries areas only, never a server's role, so the per-server office is always a grant to a person. The break-glass emergency account is one username on its own sign-in page, refused for every other account, throttled per IP and alarmed on every use. Only a person uses the admin API: a user typed as an AI agent or a service account is refused on every admin route, the approve and deny routes included, and on `POST /v1/approvals/self/enroll-token`, whatever roles it holds, with one `straza.audit.authn` failure record. Every admin request on a session re-reads the user's status and the lock denylist, so a disable or a lock binds on the next request. The connect routes and `GET /v1/self/servers` judge a session the same way. An admin API token reaches the connect routes only with apps:write for a change, names the user whose connection it changes, never starts an OAuth sign-in, and its `straza.identity.updated` record carries the token's id as `setBy` with `actorVia` `api-token` (events revision 55), and a Slack tap by a person whose Straza user is disabled or locked is refused before any decision, with one `straza.audit.authn` failure record, and the signed phone lane writes such a record when it refuses a disabled or locked person, once per approver token and reason, or a person retyped as an AI agent or a service account, once per decision. A session token minted from a key enrollment carries the key's thumbprint, and every route that verifies it needs a fresh proof from that key, so a copied token works nowhere else. An AI agent's session is bound the same way when its check-in carries a proof from the key of `straza service`, and an agent's check-in without a proof is refused on enterprise and still gets a bearer token on standalone. A browser sign-in enrolls a person's machine key only when its ID token's nonce names that key and it is at most 10 minutes old, and on the built-in issuer only a token for the straza client enrolls a key. A device code sign-in names no key, so it enrolls as a code sign-in wherever `governance.minSignIn` is `code`, the standalone default: from the straza client on the built-in issuer, and from any Straza program at an external identity provider, whose programs share one client id. `governance.minSignIn`, `browser` by default on enterprise, judges the lane at enrollment and again at every later check-in and refresh. strazad cannot see whether the sign-in asked for a new authentication or whether the identity provider honored it, so an agent that runs as the person can still enroll its own key within 10 minutes of a real sign-in, until a phone confirmation of each new machine lands. On enterprise a person's ID token alone starts no session under a coding harness name. Each such refusal writes one `straza.audit.authn` failure record, and each enrollment one `straza.audit.identity` `device.enrolled` record (events revision 47). Each such token that arrives without a valid proof is refused with one `straza.audit.authn` record with the action `proof` and the outcome `failure` (events revision 45). A proof whose nonce is missing or stale gets the nonce challenge instead, a 401 with a fresh nonce and no record, because the client signs the request again. |
| A.8.9 configuration management | Managed installs are root-owned on Linux and macOS. On macOS the managed hooks run `/opt/straza/bin/straza`, and the Straza package for macOS refuses to install while accounts other than root can change `/opt`, `/opt/straza` or `/opt/straza/bin`, because whoever could change one could swap the program the hooks run (deploy/macos/scripts/preinstall). On Windows `straza install --managed` gives `C:\ProgramData\straza` a protected DACL that lets only SYSTEM and Administrators change it, and the client trusts the managed config there only while no other account can change it or its folder (`straza doctor` shows the `managed layout` failure). At session start the server checks the hook wiring against the hashes it registers from its own rendering, and checks the binary and the configuration only against hashes an admin registers with `strazactl attestation add`. The hashes come from the client, so the `managed` level shows that the reported files match and does not prove which program reported them. |
| A.8.15 and A.8.16 logging & monitoring | Append-only hash-chained audit, Prometheus metrics, and an async pipeline whose losses are counted and logged, except four that are not counted: a crash or a kill loses the in-memory queue with no trace, a request still running 10 seconds after the stop began can lose its record with no trace, an admin, identity, authentication or approval record that fails to write leaves one warning line and no counter, and a client whose spool cannot be written logs the loss on that machine only. The cases in which a record can still be lost are among the known limits in section 5. Every admin mutation names who acted and through which credential (`actor`, `actorId`, `actorVia`: login, session or API token name, or the enroll credential on an approver enrollment). `straza.audit.authn` records every login success or failure, attestation refusals included, and every session end a person, an admin or a sweeper causes, with `sourceIp` and `userAgent` when a client connection produced it, so a session end the idle or lifetime sweeper causes carries neither. On a server that pins an object type, the `straza.audit.mcp` record of a call on a tool that names its object carries `object` with the type, the reach, the value and the id, on allow and on deny, a refusal of the object check names the held roles that bind the tool in `rolesChecked` and no role, and attribute values never ride the record. `apps.binding.create` and `apps.binding.delete` carry `covers`. A first pin, an unpin and migration 39's backfill change covers lines in place and write no binding record, so a consumer cannot rebuild a row's covers line from binding records alone. Each listing that changes a server's object list or flips its outcome writes the actorless `apps.objects.list` (events revisions 43 and 44). |
| A.8.19 installation of software on operational systems | On Linux the straza client installs from a deb or rpm package that the release job builds. The cosign-signed checksums file covers each package, and a package holds the same straza binary as the Linux archive of its architecture, whose syft SBOM lists the binary's modules. The packages carry no OpenPGP signature and no apt or dnf repository serves them yet, so the checksum check is what proves the file. The package installs `/usr/bin/straza` owned by root, the units of `straza service` with systemd's hardening, and the straza-service OS account, and no package script runs `straza install`. On Linux `straza install --managed` runs only where the package installed `/usr/bin/straza`, never copies a binary, and refuses served wiring whose hooks run another path. Purging or erasing the package deletes the machine's keys, while `apt remove` keeps them for a reinstall, and no removal revokes anything at the server, so retiring a machine ends with an admin revoking its devices (guides/operate/backup-and-upgrade.md). On Windows amd64 the straza client installs from one MSI that the release job builds (deploy/windows/straza.wxs). The cosign-signed checksums file covers it, and it holds the same `straza.exe` as the Windows amd64 zip, whose syft SBOM lists the binary's modules. The MSI installs `C:\ProgramData\straza\bin\straza.exe`, locks `C:\ProgramData\straza` to administrators, registers `straza service` as the Windows service straza-service under the virtual account NT SERVICE\straza-service, and wires no harness. On Windows `straza install --managed` also runs only where the MSI installed its binary and never copies one. A plain uninstall removes the managed wiring and keeps the machine's keys, `PURGE=1` deletes them too, and no removal revokes anything at the server (get-started/install.md, guides/operate/backup-and-upgrade.md). The MSI and the Windows binaries carry no Authenticode signature yet, so the cosign-signed checksums file is what proves the MSI and the zip. On macOS the straza client installs from the Straza package for macOS. Releases from 2.0.0 carry it as one pkg that the release workflow's macOS job builds from the tag, signs with the Developer ID Application and Developer ID Installer identities of SynapTech s. r. o., team WMPWM57KYK, with the hardened runtime and a secure timestamp, has Apple notarize and staples (.github/workflows/release.yml, deploy/macos/build-pkg.sh). The cosign-signed checksums file covers it, and its binary is the darwin archives' straza in every byte but the code signature: build-pkg.sh compares each signed slice with the job's unsigned build through tools/machocmp, and a goreleaser post hook (deploy/macos/check-release-binary.sh) compares those builds byte for byte with the archive binaries before any draft exists. Releases from 1.1.2 and earlier carry no pkg, no deb or rpm package and no MSI, and where no pkg is available an administrator builds it on a Mac from the source tree with deploy/macos/build-pkg.sh. The package installs one universal `/opt/straza/bin/straza` owned by root, links `/usr/local/bin/straza` and `/usr/local/bin/git-remote-straza` to it, creates the hidden _straza-service account with a free user ID from 450 to 499, runs `straza service` as the launchd daemon ai.straza.service under that account, and wires no harness. On macOS `straza install --managed` also runs only where the package installed its binary and never copies one. `sudo straza installer uninstall` removes the managed wiring and the package's files and keeps the machine's keys, `--purge` deletes them and the account too, and no removal revokes anything at the server (get-started/install.md, guides/operate/backup-and-upgrade.md). Jamf Pro and Intune install the pkg and the managed install with a Managed Login Items profile for the team identifier, so the service cannot be switched off in System Settings (guides/govern-an-agent/deploy-with-jamf.md and deploy-with-intune.md, not yet run on a tenant). A package built from source without the administrator's own Developer ID identities is unsigned and not notarized. |
| A.8.24 cryptography | See [Keys, certificates and tokens](https://docs.straza.ai/security/keys-certificates-and-tokens/); keys rotate (signing keys staged, active, retiring, retired: `strazactl signing-keys rotate session` stages a key every replica holds before any replica signs with it, and the previous key retires once every credential it signed has expired; the database holds one active session key and one active snapshot key, so replicas that start together sign with the same key; the client assertion key, purpose `client_assertion`, follows the same life cycle with its private half sealed under the sealing key, one staged and one active key enforced by the database, and create, rotate and retire open to a full administrator only, each leaving one audit record). A DPoP proof (RFC 9449) is an Ed25519 signature by a key the machine holds over the request's method and path and a server nonce. The nonce is a 60-second window plus an HMAC under a key in the settings table that every replica shares, a proof sent with a session token also hashes that token (`ath`), and a proof id is refused a second time for three minutes, on the same replica for a request with a session token and on every replica for a key enrollment, a key check-in, whose proof also signs the check-in counter, or an AI agent's check-in (spec/session-token revisions of 2026-10-20 and 2026-10-21). |
| A.8.26 application security requirements | Every object declaration, whether a server's own `ai.straza/object` marks or a person's pinned `straza.objects` block, carries three promises strazad cannot check: a call touches only the object its argument names, the value names exactly one object at the time of the call with no rename redirect, alias or case folding, and the server accepts calls only from the gateway or checks a credential only the gateway can obtain (app-manifest rev 7, section 7.4). The documentation states them where a server author and an operator read them. strazad decides only from the pinned copy, a tool the copy leaves out counts as reaching every object, and a live mark the pinned reach no longer meets keeps the tool to roles on every object until a person publishes the change. A draft refuses an argument that is not a required top-level string of the tool's input schema while the server runs and lists the tool. A draft of a server that is not running gets an unchecked line instead, which does not block the publish, and the gateway refuses every call that does not carry the argument as a string. The gateway refuses arguments that are not valid UTF-8, repeat a key or carry a case twin of the argument, and forwards them as sent, so the server reads the object the gate checked. A call a role on some objects admits carries the object's id as `_meta["ai.straza/object-id"]` for the server to check, and an agent's own `_meta` never reaches the server. |
| A.8.28 secure coding | For the product: test-first policy/crypto code, gosec + govulncheck in CI, invariants enforced by tests. For the operator: Straza governs AI-written code paths. |
| A.8.29 security testing in development and acceptance | The end-to-end suite in test/e2e-matrix walks scenarios written from the spec, never from the code, against the binaries built from the tree on every pull request: provisioning, enrollment, policy decisions on every hook dialect, approvals, tickets and grants, deprovisioning and the audit chain, with the propagation timers reported, and one scenario on a stack with minute lifetimes proves the token refresh, the credential renewal and expiry, the session lifetime close, the offline grace window and a signing-key rotation under live sessions. The conformance corpora replay in the unit suite and the harness matrix runs the vendor CLIs against the built binaries every week. |
| A.8.32 change management (also NIS2 21(2)(e)) | Every change to a server's manifest, roles, access rows, implications and policy sets made over the admin API, with strazactl or through the apps directory is a draft first. Pausing a server, its secrets and assignments stay immediate operations by design. A file in the apps directory proposes a draft that a person publishes, and a file that goes proposes the server's removal the same way, so the directory never changes a live server by itself. strazad checks a draft against live state and answers a verdict: the refusals that block it, the risks a publisher confirms with a tick or by typing the text the check names, once for several lines of one kind, the warnings, who gains which tool on which server, and which objects each role covers on a server that pins an object type. A covers line that makes a held role reach more objects is such a risk (openapi 0.149.0). The publish is the change record. One transaction writes the objects, the before and after of each in `draft_changes`, and the audit records, and a draft whose objects moved after its check is refused as stale. `draft.publish` carries the revision, the items, the resulting snapshot, the risk digest the publisher reviewed and the keys of the risks confirmed, never a typed text or a document, and every record the publish writes carries the same `draft` (events rev 37). When the publisher accepted an AI agent's draft that loosens a policy set binding that agent, `agentLoosened` names the set and `actor` the person who accepted it (events rev 51). `strazactl drafts revert` makes a new draft that undoes a published one, checked like any other. The direct admin routes keep their requests and answers and publish a one-item draft in the same request, so their records carry `draft` too, and a saved edit of a live policy set is a draft that activate publishes. A server's object declaration changes only through a draft, and so does every covers line a person writes. The first pin of a server's type gives every existing row `covers: every`, its reach before the pin, so a pin changes no role's coverage, though from then on the gateway refuses a call whose object argument it cannot read. A first pin, an unpin and migration 39's backfill change covers lines in place and write no binding record (events rev 44). The object list itself follows the source system without a draft, the way an assignment from the identity manager does: an object created later is covered at once by every role on every object, a renamed object stays covered by the roles that name it once a listing sees the new name, and each listing that changes the list is recorded. |

## 3. EU AI Act: Reg. (EU) 2024/1689, as amended by Reg. (EU) 2026/1744

The Digital Omnibus on AI, Regulation (EU) 2026/1744, entered into force on
2026-07-27 and moved the dates of the high-risk chapter. Read the dates below
against the consolidated text on EUR-Lex before you cite them in a contract or
a filing.

### 3.1 Does the Act bind Straza itself? No

Straza is a deterministic policy/audit/approval layer: match rules, token
crypto, hash chains, with **no ML inference anywhere in any shipped binary**.
Under Art. 3(1) as construed by the Commission's guidelines on the AI-system
definition (2025-02-06; Recital 12 carve-out for systems operating on rules
"defined solely by natural persons"; discriminator = the capacity to infer,
unchanged by the omnibus), Straza is **not an AI system**, and it is not a
GPAI model. The same holds for the kits under kits/. So: no
provider/deployer obligations, no conformity assessment, no CE marking, no
registration attach to shipping Straza. (The **CRA** is the regulation that
*does* bind the product; see §4.)

Straza does not claim that it makes you AI Act compliant, and adding an
inferential component would change this analysis for that feature.

### 3.2 What Straza gives an AI Act deployer/provider of agent systems

| AI Act | Duty (who, from when) | Straza contribution |
|---|---|---|
| Art. 5 | Prohibited practices (everyone; in force) | Deny lanes enforce an organization's internal bans on prohibited-use patterns; the audit chain proves what agents did and did not do. Marginal by design, since this is an organizational duty. |
| Art. 4 | AI literacy (effort duty; in force) | Knowledge packs push role-bound usage rules into every session; training records remain the operator's. |
| **Art. 50(1)** | Disclose AI nature **and on whose behalf the agent acts** (providers of human-interacting systems, incl. agents per the 2026-07-20 guidelines; **from 2026-08-02**) | Binding each session to a person and on-behalf attribution (per-user impersonation toward governed tools, AI agent identity in the identity manager) is exactly the substrate that disclosure needs. The disclosure UX itself belongs to the agent product. An approval step does not make an agent's output a human interaction. Machine-to-machine traffic with no human-facing output is outside Art. 50(1). |
| Art. 12 | Logging by design (high-risk; 2027-12-02) | Hash-chained CloudEvents audit of every governed call (exact command, arguments, paths, decision, rule, policy snapshot), plus prompt/reply capture. |
| Art. 14 | Human oversight able to intervene/interrupt (high-risk; 2027-12-02) | `mode: approve` gates (console/Slack/mobile), SoD via `selfApproval: false`, a person's decision on their own request accepted only when an enrolled phone or browser signs it (`approval.unsignedOwnDecisions` off, the default), coding-harness sessions refused on every decide route, fail-closed enforcement, kill switch (an identity manager deactivation revokes the sessions in seconds). An admin login can enroll a new approval device for its own user, so an AI agent that can use its person's admin login can enroll a device of its own and decide the requests that person may decide. |
| Art. 19 / 26(6) | Keep logs for at least 6 months (high-risk; 2027-12-02) | Audit chain is **append-only, and no pruning janitor exists in the codebase**; SIEM sinks give long-horizon archival. Transcript and approval stores DO prune: for high-risk deployments raise `governance.captureRetention` and `approval.retention` (defaults 30 d) to at least 4380 h, or rely on the SIEM copy. |
| Art. 26(2) | Assign competent human oversight (high-risk) | Approver roles (their own role kind, so the oversight population certifies as a distinct class), role-gated catalog, and bindings: named humans with actual authority over specific tools. |
| Art. 26(5) | Monitor operation; suspend and inform when risk manifests (high-risk) | Near-live audit, SIEM feed, and the kill switch as the suspend mechanism. |
| Art. 72/73 | Post-market monitoring; serious-incident reporting (high-risk) | Evidence: transcripts search, audit export, `strazactl audit verify` integrity proof. The report itself is the operator's. |

Most AI *coding/ops* agent deployments are not Annex III
high-risk uses. For them, the Act today means Art. 5 + Art. 4, and Art. 50
from 2026-08-02 where agents face humans; the Chapter III rows above become
live only if the use case is high-risk, and only from 2027-12-02.

### 3.3 What Straza does NOT do (AI Act)

Art. 9 risk-management system, Art. 10 data governance, Art. 11 technical
documentation, Art. 15 accuracy/robustness, conformity assessment / CE /
EU-database registration, Art. 27 FRIA. These are provider-side,
organizational, or model-level. Straza supplies *evidence into* those
processes; it never constitutes them.

## 4. Product posture (what Straza itself practices)

- Secure SDLC: invariant-driven tests and conformance corpora. CI runs on
  every pull request: golangci-lint with gosec, govulncheck, the test suite
  under the race detector, a coverage floor and the end-to-end suite.
  `make security` runs govulncheck, osv-scanner and gitleaks over the tree
  and its history, and the binaries build with CGO off.
- Supply chain: pinned modules (go.sum), static binaries, `-trimpath`;
  releases ship a syft SBOM per archive, a checksums file signed with
  keyless cosign that covers every archive and, from 2.0.0, every deb or
  rpm package, whose straza binary is the one in the Linux archive of its
  architecture, the MSI and the macOS pkg, and a container image signed by
  digest. The pkg is also signed with the Developer ID of SynapTech s. r. o.
  and notarized by Apple. Its Developer ID keys and the notary key are
  secrets of the GitHub environment macos-signing, which admits only runs
  on a v* tag, apart from a one-time rehearsal that an administrator admits
  by hand, and they reach only the macOS job's steps that use them, in a
  temporary keychain the job deletes. This is relevant for the
  **EU Cyber Resilience Act** (CRA, Reg. 2024/2847: products with digital
  elements; obligations phase in through 2027) which *does* bind
  the product, unlike NIS2.
- Disclosure: SECURITY.md: private reporting through GitHub private
  vulnerability reporting or security@straza.ai, a 72-hour acknowledgment, a
  7-day triage and a 90-day fix target, and coordinated disclosure. Relevant
  to CRA Annex I part II (vulnerability handling).

## 5. Gaps and known limits

Not built yet, and listed on the roadmap: passkeys for the standalone issuer, a
device-bound client certificate, publisher signature checks on app manifests,
and an egress allowlist per MCP server. Formal certifications of the project
are not held.

The known limits of 2.0.0 follow. The
[security model](https://docs.straza.ai/security/security-model/#known-limits)
explains each one and what you can do about it.

- An agent that holds its person's login can enroll an approval device.
- The hook lane is not a security boundary, and an MCP server a user adds to a
  harness outside the gateway is that user's responsibility.
- Manifest values are stored in plain text.
- A Rego module can run past its time limit, because the server checks the limit
  only between evaluation steps.
- The attestation level comes from the client.
- Audit records can be lost, in the cases the security model lists.
- An old snapshot signing key cannot be withdrawn.

Object-scoped roles, new in 2.0.0, add these limits. The
[known limits](https://docs.straza.ai/security/known-limits/) page lists each
one with what reduces it.

- Only the gateway checks objects. The hook lane never runs the check, and no
  policy rule can name an object.
- A tool whose calls do not name the object grants only through a role on
  every object, because strazad does not check what a role's own login
  reaches.
- A role on every object covers the objects the server lists later, including
  objects no listing has seen.
- The object list is as fresh as the last listing. A role that names its
  objects is refused an object renamed since then until a listing sees the
  new name. An object created since then also needs a person to add it to
  the role's covers line once a listing holds it. A refused call asks for one
  listing at most once a minute per server, so after the first refused call
  an object reaches the list in about two minutes when a call comes again
  after a minute, and otherwise at the next 10-minute listing.
- An object deleted and made again under its old name keeps a role on the old
  id. Until the next listing the gateway sends the old id and only a server
  that checks it refuses the call. After it, the role covers nothing under
  that name until a person publishes the role again. On a server whose listing
  gives no ids, the id is the value, so a role on the old object keeps
  covering the new one after every listing, until a person narrows the role.
- The approval card shows the object only inside the arguments preview, which
  is off when `approval.preview.enabled` is false and cuts the middle of
  arguments past 2,048 bytes.
- A server pins one object type, and a tool names its object in one required
  top-level string argument.
- The object boundary rests on three promises of the server that strazad
  cannot check.

Git through a Straza grant, also new in 2.0.0, adds these limits.
The [Git through Straza](https://docs.straza.ai/guides/serve-mcp-apps/git-through-straza/)
page says what to do about each one.

- A force push is not detected, because Straza and the resource server see
  only commit ids. A branch rule at the git host that the resource server's
  credential cannot bypass blocks it.
- Policy decides per tool, not per branch, and no rule can name a branch yet.
- The git host file is one per machine, so on a machine where people enroll
  with different Straza servers it follows the server that answered last.
- Only Claude Code on Linux is wired, and a `straza service` that runs as the
  user writes a host file that the wiring does not name.
